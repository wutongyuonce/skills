# SPEC 与设计报告模板

按任务规模裁剪，不要为了填模板制造内容。小修复可以只保留相关段落；跨 module、协议、持久化、并发或资源控制的 PR 使用完整结构。

## Part A：SPEC —— 系统必须满足什么

### 1. 背景与问题

- 当前用户可见行为：
- 造成的问题：
- 受影响的用户或调用方：

### 2. 目标行为

用用户可以观察或验证的语言描述完成后的结果。

### 3. 范围与主要场景

对每个场景写清：参与者、前置状态、操作顺序、结果。

### 4. 产品 RULE 与不变量

| ID | Rule / invariant | 适用场景 | 违反时的结果 |
|---|---|---|---|

RULE 是局部事实；不要用一张规则表替代主要场景和完整流程。

### 5. 失败、取消和恢复语义

- 哪些结果属于成功、失败、未知或部分成功？
- 哪些操作可以安全重试？
- 失败后保留或回滚哪些状态？

### 6. 并发、资源与性能约束

- 顺序和一致性保证：
- 数据规模与读取/写入上限：
- 谁能观察到哪些中间状态：

### 7. 非目标

明确本 PR 不提供的行为，尤其是容易被顺手实现的更强保证。

### 8. 验收标准

| Obligation | 可观察证据 | 验证层级 |
|---|---|---|

## Part B：设计报告 —— module 如何满足 SPEC

### 1. 当前架构和数据流

只描述最终有效的数据流和控制流。

### 2. Authority、interface 与 seam

| Rule/state/error/resource | Authority module | Interface/seam | Callers | Evidence |
|---|---|---|---|---|

### 3. 失败和资源处理

说明错误在哪里产生、在哪里标准化、在哪里展示；资源在哪里测量、限制和释放。

### 4. 实现机制

说明当前采用的算法、数据结构和持久化方式，以及它们满足哪些 SPEC 义务。不要把可替换机制写成产品需求。

### 5. 已接受的取舍

列出有意放弃的更强保证、原因和用户影响。

### 6. 义务到测试的映射

| Obligation | Authority | Test | 为什么在这一层验证 |
|---|---|---|---|

### 7. 验证计划和当前结果

区分 targeted、workspace/full、CI、baseline failure 和 unavailable checks。不要把未执行的检查写成通过。

### 8. 当前实现状态

概括当前 head 已实现、尚未实现和已知限制。删除中间实现历史、废弃升级路径和一次性验证脚本。
