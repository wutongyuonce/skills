# pi-agent skill 更新流程

当用户要求「同步最新版」「升级到某版本」「核对 SDK 漂移」，或开发中发现当前 SDK 与 skill 不一致时，读本文件。仅检查版本时完成第 1 步并报告差异；用户要求同步时执行完整流程。目标是让 SDK 参考、场景示例和入口说明共同对应一个经过验证的发布版本。

`SKILL.md` 顶部的版本基线是已核对版本的唯一声明。更新过程中保留旧基线，全部验收后再提高。普通开发按项目实际依赖版本查资料；维护 skill 不顺带升级用户项目或全局 Pi。用户已要求同步时，完成范围内的文档修改和验证，无需再次询问是否可以修改 skill。

## 1. 固定本次目标

读 `SKILL.md` 的基线，并查询发布信息：

```bash
npm view @earendil-works/pi-coding-agent dist-tags --json
```

用户指定版本时使用该版本；要求最新版时取 `dist-tags.latest`，把结果固定为明确版本，后续命令均使用这个版本。每次重新查询，文档中不保存一个长期有效的「最新版」常量。

```bash
# TARGET_VERSION 填本次查询得到的版本；此处只读取包元数据
TARGET_VERSION='<目标版本>'
npm view "@earendil-works/pi-coding-agent@$TARGET_VERSION" version engines dependencies repository dist.integrity gitHead --json
```

记录旧基线、目标版本、查询日期、Node 要求和关联包依赖范围。区分三个版本：skill 基线、用户项目依赖、当前运行的 Pi。全局 Pi 已升级不代表 skill 或项目已升级。

**完成条件**：目标是一个明确发布版本，有元数据证据；版本不可取得时报告阻塞，保留基线。

## 2. 获取相同版本的核对材料

优先使用与目标版本一致的已安装包；核对其 `package.json`，通过锁文件或包管理器依赖树记录实际解析的关联包版本。核对旧版时同理。

没有对应包时，在临时目录下载发布包。`npm pack` 可以在安装前取得新版文档，旧项目的 `node_modules` 不会随之改变：

```bash
BASELINE_VERSION='<SKILL.md 顶部基线>'
PI_SKILL_WORKDIR=$(mktemp -d)
mkdir -p "$PI_SKILL_WORKDIR/baseline" "$PI_SKILL_WORKDIR/target"
npm pack "@earendil-works/pi-coding-agent@$BASELINE_VERSION" --ignore-scripts --pack-destination "$PI_SKILL_WORKDIR/baseline" --json
npm pack "@earendil-works/pi-coding-agent@$TARGET_VERSION" --ignore-scripts --pack-destination "$PI_SKILL_WORKDIR/target" --json
```

分别使用返回的 `filename`，在对应目录解压该 `.tgz`；内容位于 `package/`。不要猜 tarball 名字，也不要把包解压到 skill 目录中。需要关联包声明时，按实际依赖解析结果取得 `pi-ai`、`pi-agent-core` 及其他相关包，而非假设所有包版本相同。

| 材料 | 用途 |
|------|------|
| `package.json` 的 `exports` / `types` / `engines` / `dependencies` | 确认公开入口、运行要求、依赖范围 |
| `CHANGELOG.md` | 从旧基线到目标版本的完整变更区间 |
| `docs/sdk.md`、相关专题 docs | SDK 用法和官方约定 |
| `examples/sdk/`、相关扩展示例 | 可编译的使用方式 |
| `dist/**/*.d.ts` | 类型、参数、返回值、事件及公开符号 |
| `dist/**/*.js` 或对应发布提交源码 | 默认值、派发顺序、await、错误和清理语义 |

读需要核对的 Markdown 文件全文。文档之间有冲突时，以目标发布包的 exports / 类型确认 API，以实现和运行结果确认行为；记录冲突，而不是沿用一份旧说明。

远程补充资料时，从发布元数据的 `repository` / `gitHead` 定位同一发布提交。优先目标包附带的内容；GitHub 主分支只用于发现后续变化，不能充当目标版本 API 的证据。旧版材料不可取得时，用目标版本逐项复核现有条目并说明证据缺口。

**完成条件**：能定位目标版本的公开 API、官方文档和实现；记录用到的包及版本。

## 3. 建立覆盖清单

枚举 `references/sdk_doc/` 和 `references/scenarios/` 的每个文件。每个文件都要获得一种状态：已核对无需修改、需修改、已过时需移除，或阻塞；不能只抽查几个文件就提高全 skill 基线。

先读 CHANGELOG 中 **旧基线之后、目标版本及之前** 的所有发布条目，包括中间版本的 Breaking Changes、修复和行为变化。再对比两版公开入口及相关类型，找出日志未提到但 skill 有描述的变化。

按现有模块路由，记录：

| 上游变化 / 现有断言 | 证据文件与符号 | 影响的 sdk_doc / scenarios / 入口 | 所需修改 | 验证结果 |
|-------------------|---------------|--------------------------------|----------|----------|
| 一条变化或待核对断言 | 目标发布包路径 | 列出全部引用 | 更新 / 删除 / 无需改 | 通过 / 阻塞及原因 |

重点核对：

- 包根及子路径导出、兼容入口、废弃 API、schema 依赖及导入路径。
- `createAgentSession`、`AgentSession`、runtime 的参数、默认行为、返回值和清理方式。
- `session.subscribe` 与 `pi.on` 的事件归属、payload、派发次数、await / 阻塞语义及结束信号。
- 自定义工具、白名单、扩展注册、资源 reload 与错误处理。
- ModelRuntime / 认证 / Provider、会话保存与恢复、设置和上下文压缩。
- 新增 SDK 能力是否影响已有场景，或需要新增一个常用场景。

对每个变化用 `rg` 查全 skill 中的符号及相关表述，让 API 文档、场景代码和入口结论同步。CLI / TUI 的变化只有影响 SDK 集成或现有文档时才纳入；其余在覆盖清单注明范围外及理由。

**完成条件**：完整变更区间和每个参考文件都有结论，每条 SDK 相关变化都有去向。

## 4. 就近更新文档

- API 的签名与语义放在对应 `sdk_doc`；场景保留可使用的代码和必要步骤，指向 API 细节。
- 新增能力优先补入现有模块；只有独立用户意图才新增场景，并更新 `SKILL.md` 索引。
- 替换失效示例及建议，删除被替代的机制。需要支持旧项目时，明确适用版本。
- 检查全 skill 的安装命令、版本描述、官方路径、相对链接和示例导入。
- 区分当前基线版本与「某 API 在某版本引入」的历史事实；历史版本号保留正确含义，不能全局替换。

本文件拥有更新流程，`SKILL.md` 只保留版本规则与入口。`CHANGELOG.md` 保存实际完成的维护记录，不重复现役 API 说明。

**完成条件**：覆盖清单中的修改已完成，入口和所有相关引用对应相同结论。

## 5. 验证目标版本

在临时验证项目中安装固定的目标 SDK，记录锁文件及实际关联包版本，使用满足 `engines` 的 Node。将需要直接导入的包声明为验证项目依赖。优先 `--ignore-scripts` 安装；若运行需要被跳过的原生依赖构建，明确记录并在验证环境中补齐，不能将安装成功当成运行通过。

验证分三层：

1. **静态检查**：核对所有文档中的公开符号与导入入口；检查修改文件的相对链接；检索旧版本号和废弃 API，逐项解释保留原因。
2. **类型检查**：将变更涉及的代码块整理成可独立编译的最小示例，补齐文中明确省略的业务变量。使用项目的 TypeScript 工具链执行 `tsc --noEmit`（ESM 示例先检查 NodeNext 模块及解析方式），记录工具版本。上游声明阻塞 NodeNext 时保留原始错误；可另用严格 Bundler/ESNext 验证示例与完整依赖类型，但不能把另一种解析模式通过称为 NodeNext 通过。不使用 skipLibCheck、声明补丁、ts-ignore 或宽泛占位类型掩盖 SDK 问题。明确区分完整示例、需要上下文的片段、签名/伪代码及故意错误示例，不将未编译项记为通过。
3. **行为检查**：最简创建与 dispose、自定义工具、扩展加载、事件归属和结束语义、内存与持久化恢复、模型及认证变更，按本次影响范围运行最小检查。事件时序、异步阻塞、默认值与失败行为用运行证据核对。优先复用项目测试或现有测试 Provider；需要真实模型时明确环境要求。

运行会话时使用临时 cwd、隔离的 agentDir 和会话/认证路径，避免改动真实用户配置。缺少凭据、运行环境或材料导致检查未跑时，逐项标为未验证；不声称测试通过。影响核心结论的验证未完成时保留旧基线，说明已完成范围和阻塞。

**完成条件**：所有变更示例类型检查通过，相关行为检查通过，静态检查无新增失效链接；覆盖清单不存在影响升级结论的阻塞。

## 6. 提高基线并交付

验收通过后更新 `SKILL.md` 顶部基线及各处当前安装版本；复查安装命令，保留有意义的历史引入版本。向 `CHANGELOG.md` 追加本次结果：

```text
日期 / 旧基线 → 目标版本
核对来源：包版本、关联包实际版本、发布提交或 tarball 标识
文档变化：受影响模块与新增 / 删除场景
验证：实际命令及结果
限制：未验证项、范围外事项及理由；无则写无
```

最终报告列出目标版本、修改文件、验证结果和仍存在的限制。首次建立 CHANGELOG 时只记录有证据的本次维护，缺失的历史不重建。

后续可直接这样调用：

> 按 pi-agent/update.md，将这个 skill 同步到 npm latest；核对完整变更区间、全部 SDK 参考和场景，验证后更新基线与 CHANGELOG。

**完成条件**：基线、安装指引、API 文档、场景和维护记录一致，报告中清楚区分已验证与未验证。
