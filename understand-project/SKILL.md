# 看懂一个项目：给小白写「看懂 X」解析文档

写一份让**完全不了解项目的人**读完就能讲出「它解决什么问题、怎么运行、数据怎么流、改哪里能深入」的 Markdown 文档。读者诉求：**架构与运行形态非常清晰**，便于后续深入了解与二次开发。

## 0. 一条不可违背的原则：由浅到深

写作顺序永远遵守 **全局 → 局部 → 细节**，不允许一上来就讲类/接口/方法：

```text
1. 项目定位 + 全景（干什么、谁用、解决什么问题）        ← 心智锚
2. 运行形态（CLI / 服务 / daemon / web / app / 库 / 插件）← 它怎么活在机器上
3. 架构与模块（代码怎么组织、模块间什么关系）            ← 图纸层面
4. 纵向核心链路（一条真实输入逐节点流经，标注每个节点
   由哪个进程/线程/守护进程/定时任务执行）               ← 把图纸变成电影
5. 边界、失败、误区、排错
6. 深入通道：模块级类/接口解析 + 横向扩展 + 源码阅读顺序  ← 给想进一步的人
```

先让读者「看见这头大象」，再讲象腿。每节只回答一个疑问，读者不带着上一个问题的答案进入下一节。

## 1. 动手前：判定深度与侦查（不要跳过）

### 1.1 详略投向取决于两个变量（三篇样例的对照结论）

| 项目量级 | 读者需要 | 篇幅投向 |
|---|---|---|
| 小/轻量（单 CLI、单库、几千～几万行） | 宏观了解 | 5～8 章；力气花在**运行形态论证**（例 memU：它明明没装服务器，怎么定时跑起来的） |
| 小/轻量 | 深入/二次开发 | 8～12 章；可下钻到命令/子命令、核心文件级 |
| 中（有服务端/daemon/多模块） | 宏观了解 | 8～10 章：运行形态与纵向链路是主体 |
| 中 | 深入/二次开发 | 12～16 章：加入口路由、模块横向对比、症状式排错、源码文件链 |
| 大/巨型仓库（数十万行、多子系统） | 宏观了解 | 10～14 章：**概念与实体区分先行**（Agent/Conversation/MemFS 这类不切清读者必迷路） |
| 大/巨型仓库 | 深入 | 16 章内封顶：正文点到文件级为止不逐类铺开；给 6～10 步文件阅读链 |

- 规律：**篇幅投向 = 项目复杂度 +「读者要不要读源码」**。纯宏观向文档可省略源码顺序章（memU 就没写）；读者要二次开发时必须给。
- 读者细粒度不确定时主动问一句，或按上下文推断并在文首声明「本文定位：X 深度」。
- 「深入」≠ 篇幅堆砌：超 ~16 章的内容拆出去，正文只给入口与一句话职责。

### 1.2 侦查清单（结论都要能落回证据）

```text
□ 仓库规模与语言：顶层目录树、README 前 50 行、包清单/构建清单 → 判断量级与类型
□ 运行入口：bin/、cli/、cmd/、main.*、entrypoint、Dockerfile/compose、systemd、cron
□ 运行形态关键词：daemon / serve / server / worker / scheduler / cron / watchdog /
  thread / 守护 / 插件 / skill / extension / agent 集成目录
□ 一次「回合」的完整生命周期：从入口命令/请求到返回，能画出几个节点
□ 数据权威源：数据库 schema、文件树结构、状态机——别只信 README 的架构图
□ git 基线：当前 HEAD commit（文档注明，标「可能变化」）
□ 官方文档/博客/设计稿（二手参照，正文以源码运行为准）
□ 讲守护/后台前先查证：daemon 是否存在、谁拉起、崩溃/重启语义（ps/cron/systemd）
```

**事实纪律**：只写能从源码、运行、官方文档验证的内容。显式区分并标注「稳定事实」（职责边界、数据流方向、模块关系，值得花篇幅）与「易变细节」（命令参数、版本号、UI 文案，一句话带过）。Alpha/频繁变化项目在文首声明「稳定认知放在职责边界与数据流上」。

## 2. 标准骨架与每节任务

中大型适用；小型合并节号（见 1.1）。**标题必须是一句人话**（例「先看运行形态：Server 是核心运行时」，不写「运行形态」）。

```text
文首引用块（epigraph，blockquote）：
   受众声明（面向谁、需要什么前置概念） + 源码基线（commit/版本/日期） +
   易变声明（Alpha 阶段等）+ 参考资料 URL（放引言或文末，只放权威源）
1. TLDR / 它不是 X   —— 两种模板见 §3，先建立最小全局模型
2. 为什么            —— 动机/「为什么不能只用普通方案」/ 用正反例解释架构判断
3. 架构（不急着看类名）—— 模块/职责图 + 运行时真实层级，双视角并置（见 §4）
4. 运行形态          —— CLI/服务/daemon/库？常驻进程？谁拉起？定时/守护在哪（见 §5）
5. 变体差异          —— 本地版 vs 云端/其它后端/部署（有才写；用对照表）
6-8. 纵向核心链路     —— 每条 = 一条真实输入旅程，5～8 个语义层（见 §6）
9. 边界 / 概念区分 / 常见误区  —— 把最易混的词钉死（见 §7）
10. 失败形态与排错    —— 有服务/存储/异步环节时写（见 §7）
11. 总结             —— 3～5 条稳定事实 + 「如果只记一条完整主线…」text 图
12. 深入通道          —— 源码阅读顺序 + 参考资料（见 §8）
```

## 3. 开篇如何建立全局认知

- **TLDR 两种模板**：
  ① 链路式——「它做的事情可以压缩成 N 条链路」+ `text` 箭头图，随即接**否定清单**「所以它不是：…」（逐条打消最可能的误读），再落一句**正面定义**。
  ② 实体树式——章题/首句即否定（Letta：「它不是『聊天记录检索 + 向量数据库』」），正文给一棵实体树（`Agent ├─ identity ├─ Conversation A/B └─ MemFS`）。
- **第一屏先给结论性事实**（谁负责什么、谁不负责什么）。例：记忆工具不自己理解对话写总结，判断「什么重要」的是宿主 Agent。职责归属是读者最快建立的锚。
- **权威数据源尽早点名**，放在章内而非结尾（例：「AGFS 是权威内容，向量库是派生索引」「Git Markdown 才是持久事实来源」「SQLite 只保存向量，不负责计算向量」）。
- 每个架构判断尽量给正反例（该存/不该存、该用/不该用），读者靠取舍理解而非死记。

## 4. 架构怎么讲：文档视角 vs 进程真相（两个视图缺一不可）

- 手法一（先图纸后真相）：先画「文档视角的模块/职责图」（五层、每层「收到什么→做什么→产出什么」），随后运行形态章**揭穿进程真相**——同一词汇讲两遍：图负责职责（"记忆服务层"是代码职责），正文负责进程（不等于一台持续监听端口的服务器）。**明确指出两者差异点**：一般大部分一致、差异是精华。
- 手法二（先真相后图纸）：先立进程事实（Server / daemon / 插件各有实体），再给逻辑分层（接入→传输→Service→处理与检索→队列→存储）。
- 引导句规范：章节标题用「先看整体架构，不急着看类名」这类话压住读者急迫感。
- 类名只在「它恰好是真实分层边界」时出现（组合根、权威存储、Router 只做协议适配）；需要列文件时，每个文件配一行人话注释（「看了能懂什么」），并给一句拆分边界总结。

## 5. 运行形态怎么讲（最容易飘、也最值得讲实）

不要满足于「这是一个 CLI/服务」。章题即可下结论（memU：「它主要是一组 CLI」）。按序回答：

```text
1. 是什么形态：app / web / cli / 服务端 / daemon / 库 / 插件 / Agent skill——
   证据是安装产物、命令、入口文件、进程生命周期，不是 README 自述
2. 装了什么、跑起来是什么：安装产生了哪些可执行 / 本地文件 / 注册项 / 定时任务
3. 有没有常驻进程：没有就直说，并解释靠什么触发（宿主进程内执行 / cron 定时拉起 /
   事件钩子）。论证句式：「…是代码职责，不等于一台持续监听端口的服务器」；
   「每次运行 CLI 在当前进程内创建对象…随 CLI 一起退出。用户不需要另外启动 X」
4. 后台/守护部分点名：哪个环节是 daemon / 守护线程 / 异步 worker / 后台 reflection
   subagent / 定时任务；由谁拉起、与主进程什么关系、崩溃/重启语义
5. 和宿主/平台的关系（运行形态 = 扩展接入，二者绑定讲）：是独立服务（Agent 插件来
   接入）还是寄生在宿主里？画清 宿主进程 / 插件 / 自身进程 三者边界
6. 被谁拉起的进程就归谁：先讲清触发者与生命周期，再讲内部做什么
```

多进程/多线程时给图或小表：**节点 → 载体（进程/线程/daemon/cron）→ 触发时机**。需要区分「谁执行哪段」时做「执行者」表（如 prepare=纯代码 / self-evolve=模型工作 / commit=纯代码）。纠正直觉要直接（「定时器通常不直接执行 prepare：它先启动无头 Agent 并把指令交给 Agent」）。

## 6. 纵向核心链路怎么写（全文价值最高的部分）

- **切层规范**：一条真实输入切成 5～8 个语义节点，每个节点一节，标题即「这层收到什么→做什么→产出什么」；层名连读就是整条链路（宿主层→增量层→准备层→Agent 整理层→结果收集层→向量准备层→存储层→状态确认层）。层与层之间用一行 `→` text 图连接。
- **同步/异步逐层标注**：哪步同步、哪步异步要讲成时序设计，包括顺序的**理由**（例：「先把最容易失败的外部调用做完——网络错误和 rate limit 最常发生在 embedding 阶段，让它先于数据库写入完成，可保证失败时原记忆库完全不变」）。给「同步阶段 / 异步阶段」分块图与判定句（「commit 已接受只证明同步归档完成并创建了后台任务；长期记忆是否已更新要查 task 状态」）。
- **状态与失败当一等公民**：每个链路澄清「完成状态 ≠ 数据就绪」（内容已写入 ≠ 可完整检索；文件写入但未 commit ≠ 成为正式记忆；成功才推进游标，中途失败游标不前移、下次重跑这批）。可靠性模型用整张表收束：失败位置 × 已有数据是否变化 × 游标/进度是否推进 × 下次如何处理。
- 链路数 = 项目核心动词数（写入/存储、读取/检索、后台提炼/摘要各一条）；链路之间可独立成功失败要讲明——排错时逐条验证。
- 纯宏观/轻量文档可只给两条链路文字重述作结，不设独立大图。

## 7. 边界、误区与排错

- **概念区分**：把最易混的词用表钉死（本地记忆 vs 云端记忆、库 vs 服务、同步归档 vs 异步摘要、压缩 vs 检索、共享的是仓库不是身份…）。区分维度 > 长篇解释。
- **常见误区**（可选成章）：每条「错。正。」两句式，是 TLDR 否定清单的展开论证。
- **症状式排错**（有服务/存储/异步时写）：标题用用户可观测症状（「资源能浏览，但语义搜索不到」），每条给分层检查顺序 + 「不要先怀疑 X」的引导。
- **边界句兜底**：明确写出当前可靠性边界（例：「当前没有包住所有写入的总事务。这是当前可靠性边界」），比形容词可信。
- 破除跨层误解要成章（例：「支持多平台」不等于每个平台各写一套算法——宿主与 OS 是两个独立扩展轴）。

## 8. 收尾与深入通道

- **总结**：给 3～5 条**可独立验证的稳定事实**（职责边界、权威数据源、链路独立性），再给「如果只记一条完整主线，可以记成」的 `text` 流程图。轻量文档可用一段话 + 链路文字重述代替。
- **源码阅读顺序**：从运行入口一路点文件，按调用链而非文件名散读。给编号文件组，每组 = 「文件路径 + 一句该文件回答什么」，组末点明重点看什么差异；把链路终点连回行为概念（例：post-turn-reflection → reflection-launcher → memory-worktree = Dreaming 完整链路）。只在读者要深入/二次开发时提供。
- **参考资料**：官方 README/docs/blog/repo 链接；放引言 blockquote 或文末列表，不放二手。

## 9. 语言与格式规范（保持系列一致）

- 标题 `# 看懂 X：一句话副标题`（副标题点明主线）。
- 文首 epigraph 用 `>` 引用块；引言可声明受众门槛（「面向已了解 RAG 基本概念的读者」）。
- 中文正文；每出现一个**专名（命令/服务/类/文件）必配一行**人话注释；术语首次出现给中文解释，可括注英文原词。
- 不罗列类名；文件名只出现在「证据」与「源码阅读顺序」。
- **text 图分级**：链路/数据流用 `→` 单行推进；实体关系用 `├─ └─` 树；多角色流程用 `┌──▼──┐` 框；全篇唯一大图收束。图与上下文同屏可读、无外部依赖；png 尽量少用。
- 表格是第二武器：调度方式、同步/异步、边界机制、接入方式、记忆类型全部落表。
- 判定式句式高频，直给结论：「所以它不是…」「不要把 X 和 Y 混在一起理解」「…不是对话摘要的另一个名字」「…不能推导出…」。
- 版本与链接：基线走引言首行；外链只放权威源。

## 10. 交付前自检清单

```text
□ 第一章读完，读者能说出：它解决什么问题、运行形态、谁负责核心判断
□ 有没有先讲运行形态/全景，再讲类/接口？正文任何位置都没有「上来就讲类」
□ 每条纵向链路：节点 → 进程/线程/守护/定时载体 + 同步/异步 + 完成≠就绪的澄清
□ 架构「文档视角」与「进程真相」双视图齐了，差异点有说明
□ 所有结论可溯源（源码路径/官方文档/运行验证）；易变信息有基线标注
□ 有概念/误区区分；有（如适用）症状式排错；总结给稳定事实 + 一条主线
□ 深入通道按需给：读者要二次开发 → 有源码阅读顺序（文件组 + 一句目的）
□ 篇幅与 §1.1 投向规律匹配，不是越长越好
```
