# 开源项目贡献机会调研

对用户传入的每个仓库 URL 执行调研，在当前工作目录中克隆或更新仓库。

**硬性门禁：每次触发后，第一条回复必须同时询问以下三项，然后停下等待。缺任何一项都视为未完成询问。** 即使用户消息里已经写了 issue/roadmap/源码调查步骤、仓库名、“拉取到当前文件夹”、或已经点名 feat/fix，也不得跳过。在用户答完三项前禁止：克隆/更新仓库、创建任务列表、列目录、读源码、查 GitHub、写进度账本。

## 启动：询问三项，未答完不开始

1. **调研模式**：
   - **选项 1 — 全量 GitHub 审查**：全量扫描 open Issue/PR，筛出真实存在、适合贡献的 feat/fix/refactor/perf 候选。
   - **选项 2 — 源码模块审查**：先输出模块清单等用户选一个模块；用户选定模块后必须再问本模块的贡献类型和 PR 数量，答完后才只从该模块的源码、测试和配置中发现问题；形成有完整代码证据的候选后，才定向核验它是否已有 Issue/PR/commit。
2. **优先贡献类型**（可多选）：feat、fix、refactor/perf。按用户给出的顺序优先；perf 归入 refactor/perf，不单列。选中方向分别归类。未选方向不主动扩展，除非用户明确要求“全部”。
3. **找几个最合适的 PR**：本轮最终报告主推荐几个候选。默认给 2、3（推荐）、4 三个选项；用户也可自定义正整数。报告的「最值得优先贡献的机会」和「推荐贡献顺序」不得超过该数量；多出来的达标项只写入账本，不挤进主推荐。

用户三项都选定后严格按对应模式执行。只做调研和报告，不要擅自修改源码、建 issue、commit 或发 PR。

## 源码模块模式的隔离门禁

源码模块审查的价值是从代码本身发现机会，而不是先被社区待办引导后回代码找佐证。因此在具体源码候选成立前：

- 不读取、搜索或枚举 GitHub Issue、PR、Discussion、Project、milestone、roadmap、RFC 跟踪项或分支命名；
- 不建立 Issue/PR 清单，不用 `help wanted`、`good first issue`、标题关键词或 roadmap 反向选择要读的代码；
- 只看用户选定模块及其真实调用链所需的源码、测试、配置、package exports 和直接上下游；本地架构/贡献文档仅用于理解代码约束，不能用其中的 issue/roadmap 链接生成候选；
- 先完成入口可达性、上下游消费者、不变量冲突、已有防御、测试与最小交付 seam 的核验。只有达到“真实存在”门槛，才把它称为源码候选；
- 候选成立后，才针对该候选的具体符号、行为和文件路径做 Issue/PR/commit 去重。核验只回答“是否已被提出或实现”，不得顺手扩展成全量 Issue/PR/roadmap 调研；
- 若定向核验发现已有 Issue，可在报告中附链接；没有 Issue 也不要求代用户创建。发现已有 PR/commit/实现则排除或降级，不再推荐重复贡献。

用户随后要求增加另一个模块时，先按同样的纯源码流程审查新模块；不得因为上一模块已经进入 GitHub 去重阶段，就提前检索新模块的 Issue/PR/roadmap。

## 模块清单持久化与复用

源码模块审查模式必须把模块清单持久化到该项目的 `PR_HINT_PROGRESS_<repo-slug>.md`，使用户在后续轮次继续选择模块时不必重复盘点。模块清单是用户最常读取的当前状态，必须放在文档标题之后、所有 `Round` 之前，固定使用二级标题 `## 当前模块清单`；不要把唯一一份清单埋在某个历史轮次里。

- 首次进入源码模块审查时，在开始源码深入分析前建立或打开账本；完成结构级盘点后，把清单写入文档开头的“当前模块清单”，并在当前轮次记录“本轮生成了顶部清单”。每个模块至少记录：名称、路径、职责摘要、关键入口/目录、测试位置、适合的贡献方向或边界；清单头部记录生成时间、仓库/远程、分支、提交和状态。
- 后续用户再次选择源码模块审查时，必须先读取该项目已有进度账本。若账本中的模块清单对应的仓库、分支/提交和目录仍可确认，且没有明显过时迹象，直接复用清单并让用户选择模块；不要重复列目录或重新扫描整个项目。
- 复用前至少做轻量新鲜度检查：确认仓库路径和远程仍匹配，检查当前分支/提交是否变化，并确认清单列出的关键目录仍存在。只做这些检查，不提前深入模块源码、Issue 或 PR。
- 以下任一情况成立时，标记旧清单“需要刷新”，再重新进行结构级盘点：账本不存在或没有明确模块清单；仓库远程或路径不匹配；记录的提交不可定位且目录结构已发生明显变化；关键模块路径消失/重命名；用户明确要求刷新；或上次盘点与当前仓库状态相差过大，无法可靠判断模块边界。
- 清单复用、刷新和用户选择都要在账本中追加新轮次记录，不能覆盖历史轮次。复用时不要复制整份清单，只记录检查时间、检查依据和“沿用顶部当前模块清单”。刷新时更新顶部清单，并在新轮次记录刷新原因及模块增删改摘要，使顶部保持易找、轮次保留变化历史。
- 如果账本只有部分模块清单仍然有效，保留有效部分并明确标记过时项；在用户选择模块前补齐结构盘点，不能静默混用新旧清单。

## 贡献类型与候选门槛

| 类型 | 关注点 |
|---|---|
| feat | 是否有必要、用户价值是否明确、能否切出清晰实现 seam 与独立交付边界；小功能切成最小可交付单元，大功能只建议认领其中一块 |
| fix | 沿上下游执行链确认入口可达、问题真实发生、预期不变量与实际行为冲突，并给出最小修复边界 |
| refactor/perf | 性能/精简/去重/可维护性问题有真实证据（基准、复杂度、重复路径、维护成本），行为不被无依据改变，有可独立交付的 seam；perf 归入此类，不单列 |

候选筛选门槛（三者都满足才入候选）：
- 没有相关 PR、commit 或已有实现；
- 尚未解决，或关闭原因并非已解决；
- 描述足够清晰，能定位预期行为和影响范围。

排除项要记录理由：“已解决”“已有 PR/commit”“重复 issue”“描述不清”。若用户要求审计筛选过程，须给出排除说明。

## 报告写作与候选详情

报告先给结论，再给证据。用直接、具体的中文说明“谁在什么条件下调用了什么、数据或状态经过哪些步骤、哪里出现了什么结果、为什么值得贡献”。少用抽象术语；必须使用术语时，第一次出现就说明它在本项目中的实际含义。证据与论证文字不要用比喻、宣传语或只复述 issue/PR 标题（fix 候选末尾的“人话版”例外）。

每个候选都要有能支撑判断的详情，表格只做索引。每个候选最后给出一句人话结论：`值得做/暂不建议做/待验证`，说明决定它的关键事实；上下游或外部状态无法确认时，明确写出缺口，不用肯定语气补齐。

**fix 候选必须另给“人话版”（必写）**：按 背景 → 问题 → 修法 的顺序，让不熟悉本项目的读者独立读懂。
- 这功能平时怎么工作：为用户解决什么，正常路径上做了什么（专业名词第一次出现就解释）。
- 坏在哪里 / 为什么发生 / 影响什么：哪种数据或操作会触发，错误行为是什么，实际后果是什么。
- 修法是什么 / 为什么结果不变：改了哪一层、修正了什么，为什么正常场景的结果与修复前一致。

人话版写在证据字段之后，必须独立可读；复杂 PR 可写长，但不许只堆代码符号。证据字段保持精确定位；人话版允许日常类比，但须准确对应机制，不因生动牺牲准确。feat/refactor/perf 候选按类型说明必要性、缺口、入口/seam、边界、验证方式。

## 强制进度记录

除最终报告外，每个项目维护独立 Markdown 进度账本 `PR_HINT_PROGRESS_<repo-slug>.md`（当前工作目录，一项目一文件）。开始任何检索前先创建/打开，每批重要检索后更新；只记录实际完成的工作，不用计划冒充完成。

账本用**追加轮次**记录，不覆盖历史。每轮写：编号、模式、开始/截止时间（完整日期+时区）、优先类型排序、本轮主推荐数量、检索范围与方法、实际完成的 Issue/PR 或读过的模块/文件/测试、已确认证据与排除项、待确认/未覆盖、结论与下一轮建议。“截至某时间已完成”只代表该时间点之前的已记录范围；下一轮可复查同一批内容，必须新开轮次并保留上一轮。检索中断也要先写入中断位置和原因。

## 工作流程

1. 逐个处理 `$@` 中的仓库 URL。目录已存在时先确认其远程仓库，避免覆盖用户改动；必要时在报告中说明无法更新的原因。
2. 读项目根目录及相关子目录的 `CONTRIBUTING.md`、行为准则、开发文档、CI 说明，严格遵循其分支、测试和 PR 流程；若文档要求先讨论 Issue，只记录这项贡献约束，不跟随其中链接调查具体 Issue/PR/roadmap。源码模块模式在候选成立前只读本地文件。
3. 按所选模式调查。全量 GitHub 审查优先用 GitHub CLI 或官方页面；源码模块审查先使用本地代码工具，只有候选成立后才定向使用 GitHub。**只做调研与报告**。
   - **全量 GitHub 审查**：先获取全部 open Issue/PR（编号、标题、标签、作者、时间、链接），记录总数，不挑着看；清单完成后立即在账本写明截至时间、覆盖范围、优先类型，之后分批核验并持续更新账本。逐项检查状态、描述、评论、关联 branch/PR/commit、维护者反馈、源码现状。对 open PR 检查改动、CI、review 状态、是否覆盖某 issue、是否重复实现。报告区分：可贡献的 open Issue、已有实现的 open PR、描述不清/证据不足、已被代码抵消。
   - **源码模块审查**：先读取项目账本中的最近模块清单并按“模块清单持久化与复用”规则做轻量新鲜度检查。清单可复用时，直接输出账本中的清单供用户选择；不可复用时，只做结构级分析——模块职责、入口、关键目录、测试位置、风险/贡献边界，把实际读过的文件和新清单写入账本。先输出模块清单，等用户选定一个模块；选定前不逐函数深挖、不扫描潜在 bug、不检索 Issue/PR/roadmap。**用户选定模块后必须再次停下询问两项，未答完禁止深入该模块源码、创建深挖任务、查 GitHub：**（1）本模块优先贡献类型（feat / fix / refactor/perf，可多选）——不得因为启动时已选过就跳过，启动答案只能作为选项默认值，仍须再问并等答；（2）本模块找几个最合适的 PR（正整数）——同样不得沿用启动数量直接开干。两项都得到回答后，才以该模块为一轮，按本模块确认的类型和数量审查源码、测试、配置和必要的上下游。必须先完成第 4 步的真实性核验并形成源码候选，才能执行第 5 步的定向 GitHub 去重。
4. **先完成源码真实性核验**（不只凭单个函数/单段代码下结论）。对每个潜在 bug、源码改进点和重要 feature：
   - 从入口（用户输入/API/事件/任务）向下追踪参数、状态、数据如何经过调用者/被调用者/队列/库/缓存/序列化/外部服务；再向上追踪谁消费、展示、触发后续。
   - 记录问题成立的前置条件、预期不变量与实际行为；检查上下游是否已做校验、归一化、重试、去重、限流、兜底或错误处理。
   - 搜全部直接调用者、同类实现、相关测试、配置默认值、部署路径，确认问题不在不可达代码、测试桩或废弃流程中。
   - 用最小复现、现有测试、日志/接口行为或静态链路证明影响；只能推测时标“推测/待验证”。有已有防御或相反证据时给出结论：真实存在 / 仅特定配置存在 / 已被上下游抵消 / 不成立；上下游信息不全时说明缺失环节与原因。
   - 若后续状态会重触发 effect/任务/请求/事件，检查是否导致重复执行、竞态或资源泄漏；有防抖/清理/幂等保护则纳入结论。
5. **源码候选成立后才做定向 GitHub 去重**（仅模块模式）。先用候选涉及的符号、行为、文件路径和错误表现搜索是否已有 Issue；若找到 Issue，再按序核对并记录：
   1. Issue 页面 `Development` 区域的所有 branch/PR 关联（含已关闭、草稿、非默认分支）；
   2. 搜索仓库内引用该编号或候选关键符号/行为的 PR；
   3. 检查 PR 标题/正文/评论/提交/分支名，识别没有自动关闭关键词的实现；
   4. 检查默认分支及相关分支提交历史是否已有实现或后续合并；
   5. 以上均无关联且数据访问无失败，才标记“无相关 PR/commit”。访问不完整/超时/失败时标记“关联状态待确认”，不列为干净候选。
   已关闭但未合并的相关 PR要单独报告其状态、关闭原因、是否保留实现分支、是否需等维护者意见再 follow-up。GitHub `Development` 区域与搜索结果冲突时保留两种结果、标注检查时间，并取保守结论。完成一个候选的去重后回到代码候选池，不浏览无关 Issue、PR 或 roadmap。
6. **仅全量 GitHub 审查模式**查 roadmap、计划、RFC、讨论区和维护者公开规划，列出社区可实现且未完成的事项，并检查代码、已有 PR、上下游依赖。源码模块审查模式完全跳过 roadmap/计划/RFC/讨论区，不设置 `Roadmap 事项` 候选。
7. 为每个发现记录证据：源码文件与行号、上下游调用链、前置条件、复现或推理依据、影响范围、置信度；Issue/PR/commit 链接仅在源码候选成立后的去重阶段记录，roadmap 链接仅用于全量 GitHub 审查。不凭标题、单函数或搜索摘要下结论。
8. 按下方结构输出中文 Markdown 报告；没有可靠发现的类别写“未发现符合条件的事项”，不为凑数量猜测。报告加“调研进度与截止时间”小节，注明对应账本与轮次、截至时间、覆盖/未覆盖范围；账本与报告都保留，不得用报告替代账本。

## 判断原则

- “真实存在”必须同时有问题点和可达执行链：至少说明入口、关键中间处理、下游消费者、预期与实际差异。只有可疑代码、未证明影响真实流程的，最多列“待验证”，不推荐直接提交 PR。
- 不能因局部函数有风险就跳过上下游检查；确认调用方是否传入该值、下游是否已过滤/修正、错误是否被重试或吞掉、对应分支是否真会在生产配置执行。
- 不把代码风格偏好包装成 bug；每个 bug 至少有代码证据、可复现路径或明确的不变量冲突。
- 优先推荐小范围、可验证、符合项目当前架构的贡献；不引入全新框架或大型重构。
- 报告主推荐（总结里的最值得优先贡献机会 + 推荐贡献顺序）不得超过用户指定的 PR 数量；超出部分只写入账本。
- 每个 fix 候选的人话版必须脱离项目背景独立读懂；术语只在首次带解释后使用；不得在无人话版的表格行里以一句“修复建议”了事。
- 研究资料只用于支持判断，不大段复制；链接直指原始 issue、文档、源码、PR、commit、项目或论文页。
