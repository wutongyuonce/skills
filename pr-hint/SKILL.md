# 开源项目贡献机会调研

对用户传入的每个仓库 URL 执行调研，并在当前工作目录中克隆或更新仓库。**每次触发本 skill 后，都必须先询问模式并等待用户回答，再克隆仓库或执行任何调查。** 不要因为用户只说“拉取/克隆项目”就跳过询问。

> 你希望我审查你指定的 GitHub issue/PR，还是自动寻找新的贡献机会？

允许用户回答“仅拉取/只克隆，不调研”；此时只完成仓库拉取，不再调查 issue、PR、roadmap 或源码。若用户选择审查指定的 issue/PR，要求其提供 issue/PR URL、编号或明确的筛选范围；若只提供仓库 URL，则审查该仓库中与用户描述直接相关的 issue/PR，不要自行扩大为全量机会搜索。若用户选择自动寻找，则按“自动发现模式”执行。只做调研和报告，不要擅自修改项目源码、创建 issue、提交 commit 或发起 PR。

## 工作流程

1. 逐个处理 `$@` 中的仓库 URL。若目标目录已存在，先确认其对应的远程仓库，再避免覆盖用户已有改动；必要时在报告中说明无法更新的原因。
2. 阅读项目根目录及相关子目录中的 `CONTRIBUTING.md`、行为准则、开发文档和 CI 说明。严格遵循其中的 issue、分支、测试和 PR 流程；若文档要求先讨论 issue，只能把建议写入报告，不要代替用户提交。
3. 按用户选择的模式调查 GitHub issue/PR，优先使用 GitHub CLI 或 GitHub 官方页面。
   - **指定审查模式**：逐项核对用户给出的 issue/PR，检查是否仍然有效、是否已有实现、关联 PR/commit、维护者反馈、源码现状和可行的解决方案。不要把未被用户指定的条目自动列为候选。
   - **自动发现模式**：筛选同时满足以下条件的候选：
     - 没有相关 PR、commit 或已有实现；
     - 尚未解决，或关闭原因并非已解决；
     - 问题描述足够清晰，能够定位预期行为和影响范围。
   - **关联 PR 排查是候选筛选的硬性前置条件，不得只看 issue 页面摘要或一次 GitHub API 返回结果。对每个候选 issue，按以下顺序核对并记录结果：**
     1. 查看 issue 页面 `Development` 区域中的所有 branch/PR 关联，包括已关闭、草稿和非当前默认分支的 PR；
     2. 搜索仓库内引用该 issue 编号的所有 PR，至少覆盖 `"#<issue-number>"`、`fixes #<issue-number>`、`closes #<issue-number>`、`resolves #<issue-number>` 及其大小写变体；
     3. 检查 PR 标题、正文、评论、提交信息和分支名，识别“实现了该 issue 但没有使用自动关闭关键词”的关联；
     4. 检查默认分支和相关 PR 分支的提交历史，确认是否已有实现或后续合并；
     5. 只有在以上检查均无关联且数据访问没有失败时，才能标记为“无相关 PR/commit”。GitHub 页面/API/CLI 访问不完整、超时或失败时，标记为“关联状态待确认”，不得列为干净候选。
   - 发现已关闭但未合并的相关 PR 时，不得把 issue 当作无 PR 候选；应单独报告 PR 状态、关闭原因、是否保留实现分支，以及是否需要等待维护者意见后再做 follow-up。
   - GitHub `Development` 区域与搜索结果可能因权限、缓存或动态加载而不一致；截图、页面上的 branch/PR 关联和可直接打开的 PR 链接都属于证据，不能被“当前 API 返回为空”覆盖。出现冲突时保留两种结果并标注检查时间，优先采取保守结论。
4. 回到本地源码核实每个候选 issue：定位相关文件、函数、测试或配置，说明问题为何真实存在；若无法复现或证据不足，标记为“待验证”，不要当作确定缺陷。
5. **强制执行上下游真实性核验，不得只根据单个函数或单段代码下结论。** 对每个候选 bug、源码改进点和重要 feature，沿真实执行链路检查：
   - 从用户输入、API、事件或任务入口开始，向下追踪参数、状态和数据如何经过调用者、被调用者、队列/数据库/缓存、序列化层和外部服务；再向上追踪结果由谁消费、展示或触发后续动作。
   - 明确记录问题成立所需的前置条件、预期不变量和实际行为，检查上下游是否已经做了校验、归一化、重试、去重、限流、兜底或错误处理。
   - 搜索所有直接调用者、同类实现、相关测试、配置默认值和部署路径，确认问题不是只存在于无法到达的代码、测试桩或已废弃流程中。
   - 用最小复现、现有测试、日志/接口行为或静态执行链路证明影响确实会发生；如果只能推测，必须标记为“推测/待验证”，不得列为“可直接提交 PR”的问题。
   - 对已有防御逻辑或相反证据给出结论：问题是真实存在、仅在特定配置下存在、已被上下游抵消，还是不成立。若上下游信息无法完整获取，也要说明缺失环节和不能确认的原因。
6. 查看项目官方 roadmap、计划、RFC、讨论区和维护者公开规划，列出社区可以实现且尚未完成的事项。区分“官方明确计划”和“基于源码推断的建议”。对 roadmap 事项同样检查当前代码、已有 PR 和上下游依赖，避免推荐已经实现或无法独立交付的事项。
7. 深读与项目主题相关的源码，寻找真实的 bug、冗余代码或可精简接口，以及有明确价值的 feature。参考相关优秀开源项目和高可信研究资料时，给出来源链接，并说明适配该项目的理由。任何源码发现都必须先完成上下游真实性核验，再进入候选列表。
8. 为每个发现记录证据：GitHub issue/PR/commit/roadmap 链接、源码文件及行号、上下游调用链、前置条件、复现或推理依据、影响范围和置信度。不要仅凭标题、单个函数或搜索摘要下结论。
9. 按下方结构输出一份中文 Markdown 报告。没有可靠发现的类别写明“未发现符合条件的事项”，不要为了凑数量提出猜测。

## 判断原则

- 将“已解决”“已有 PR/commit”“重复 issue”和“描述不清”的条目排除在候选之外，并说明排除理由（如用户要求审计筛选过程）。
- 不把“代码风格偏好”包装成 bug；每个 bug 至少给出代码证据、可复现路径或明确的不变量冲突。
- “真实存在”必须同时有问题点和可达执行链路：至少说明入口、关键中间处理、下游消费者以及预期与实际行为的差异。只发现可疑代码但没有证明它会影响真实流程时，最多列为“待验证”，不能推荐直接提交 PR。
- 不能因为某个局部函数看起来有风险就跳过上下游检查；尤其要确认调用方是否传入该值、下游是否已经过滤/修正、错误是否会被重试或吞掉，以及对应分支是否真的会在生产配置中执行。
- 如果后续状态会重新触发 effect、任务、请求或事件，必须检查该状态更新是否会导致重复执行、竞态或资源泄漏；如果有防抖、清理或幂等保护，要把它纳入结论。
- 优先推荐小范围、可验证、符合项目当前架构的贡献；不要为了提出建议而引入全新框架或大型重构。
- 研究资料只用于支持判断，不要大段复制内容；链接应直接指向原始 issue、文档、源码、PR、commit、项目或论文页面。
