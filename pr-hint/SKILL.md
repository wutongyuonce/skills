# 开源项目贡献机会调研

对用户传入的每个仓库 URL 执行调研，在当前工作目录中克隆或更新仓库。

**硬性门禁：每次触发后，第一条回复只能是询问调研模式，然后停下等待。** 即使用户消息里已经写了 issue/roadmap/源码调查步骤、仓库名或“拉取到当前文件夹”，也不得跳过询问。在用户回答前禁止：克隆/更新仓库、创建任务列表、列目录、读源码、查 GitHub、写进度账本。

## 启动：询问两项，未答前不开始

1. **调研模式**：
   - **选项 1 — 全量 GitHub 审查**：全量扫描 open Issue/PR，筛出真实存在、适合贡献的 feat/fix/refactor 候选。
   - **选项 2 — 源码模块审查**：只做模块级分析，先输出模块清单等用户选一个模块，再深审该模块。
2. **优先贡献类型**（可多选）：feat > fix > refactor，按用户顺序优先，选中方向分别归类。

用户选定后严格按对应模式执行；未选方向不主动扩展，除非用户明确要求“全部”。只做调研和报告，不要擅自修改源码、建 issue、commit 或发 PR。

## 贡献类型与候选门槛

| 类型 | 关注点 |
|---|---|
| feat | 是否有必要、用户价值是否明确、能否切出清晰实现 seam 与独立交付边界；小功能切成最小可交付单元，大功能只建议认领其中一块 |
| fix | 沿上下游执行链确认入口可达、问题真实发生、预期不变量与实际行为冲突，并给出最小修复边界 |
| refactor | 性能/精简/去重/可维护性问题有真实证据（基准、复杂度、重复路径、维护成本），行为不被无依据改变，有可独立交付的 seam |

候选筛选门槛（三者都满足才入候选）：
- 没有相关 PR、commit 或已有实现；
- 尚未解决，或关闭原因并非已解决；
- 描述足够清晰，能定位预期行为和影响范围。

排除项要记录理由：“已解决”“已有 PR/commit”“重复 issue”“描述不清”。若用户要求审计筛选过程，须给出排除说明。

## 报告写作与候选详情

报告先给结论，再给证据。用直接、具体的中文说明“谁在什么条件下调用了什么、数据或状态经过哪些步骤、哪里出现了什么结果、为什么值得贡献”。少用抽象术语；必须使用术语时，第一次出现就说明它在本项目中的实际含义。证据与论证文字不要用比喻、宣传语或只复述 issue/PR 标题（fix 候选末尾的“人话版”例外）。

每个候选都要有能支撑判断的详情，表格只做索引。每个候选最后给出一句人话结论：`值得做/暂不建议做/待验证`，说明决定它的关键事实；上下游或外部状态无法确认时，明确写出缺口，不用肯定语气补齐。

**fix 候选必须另给“人话版”（必写）**：按 背景 → 问题 → 修法 的顺序，让不熟悉本项目的读者独立读懂。
- 这功能平时怎么工作：为用户解决什么，正常路径上做了什么（专业名词第一次出现就解释）。
- 坏在哪里 / 为什么发生 / 影响什么：哪种数据或操作会触发，错误行为是什么，实际后果是什么。
- 修法是什么 / 为什么结果不变：改了哪一层、修正了什么，为什么正常场景的结果与修复前一致。

人话版写在证据字段之后，必须独立可读；复杂 PR 可写长，但不许只堆代码符号。证据字段保持精确定位；人话版允许日常类比，但须准确对应机制，不因生动牺牲准确。feat/refactor 候选按类型说明必要性、缺口、入口/seam、边界、验证方式。

## 强制进度记录

除最终报告外，每个项目维护独立 Markdown 进度账本 `PR_HINT_PROGRESS_<repo-slug>.md`（当前工作目录，一项目一文件）。开始任何检索前先创建/打开，每批重要检索后更新；只记录实际完成的工作，不用计划冒充完成。

账本用**追加轮次**记录，不覆盖历史。每轮写：编号、模式、开始/截止时间（完整日期+时区）、优先类型排序、检索范围与方法、实际完成的 Issue/PR 或读过的模块/文件/测试、已确认证据与排除项、待确认/未覆盖、结论与下一轮建议。“截至某时间已完成”只代表该时间点之前的已记录范围；下一轮可复查同一批内容，必须新开轮次并保留上一轮。检索中断也要先写入中断位置和原因。

```markdown
# pr-hint 进度：<repo>

## Round 1
- 模式：全量 open Issue/PR / 源码模块
- 开始：YYYY-MM-DD HH:mm TZ
- 截止：YYYY-MM-DD HH:mm TZ
- 本轮范围：...
- 已完成：...
- 证据与排除项：...
- 待确认/未覆盖：...
- 下一轮：...
```

## 工作流程

1. 逐个处理 `$@` 中的仓库 URL。目录已存在时先确认其远程仓库，避免覆盖用户改动；必要时在报告中说明无法更新的原因。
2. 读项目根目录及相关子目录的 `CONTRIBUTING.md`、行为准则、开发文档、CI 说明，严格遵循其 issue/分支/测试/PR 流程；若文档要求先讨论 issue，只把建议写入报告，不代替用户提交。
3. 按所选模式调查，优先用 GitHub CLI 或官方页面。**只做调研与报告**。
   - **全量 GitHub 审查**：先获取全部 open Issue/PR（编号、标题、标签、作者、时间、链接），记录总数，不挑着看；清单完成后立即在账本写明截至时间、覆盖范围、优先类型，之后分批核验并持续更新账本。逐项检查状态、描述、评论、关联 branch/PR/commit、维护者反馈、源码现状。对 open PR 检查改动、CI、review 状态、是否覆盖某 issue、是否重复实现。报告区分：可贡献的 open Issue、已有实现的 open PR、描述不清/证据不足、已被代码抵消。
   - **源码模块审查**：拉取并读贡献文档后只做结构级分析——模块职责、入口、关键目录、测试位置、风险/贡献边界，把实际读过的文件写入账本。先输出模块清单，等用户选定一个模块再深入；选定前不逐函数深挖、不扫描潜在 bug、不检索 Issue/PR。选定后以该模块为一轮，按所选类型审查。模块模式在形成具体源码候选前不建 Issue/PR 全量清单；只有候选形成后才做定向关联核验。
4. **候选筛选：关联 PR 排查是硬性前置条件，仅在候选形成后执行**（模块模式）。对每个候选 issue 按序核对并记录：
   1. issue 页面 `Development` 区域的所有 branch/PR 关联（含已关闭、草稿、非默认分支）；
   2. 搜索仓库内引用该编号的 PR（`#N`、`fixes #N`、`closes #N`、`resolves #N` 及大小写变体）；
   3. 检查 PR 标题/正文/评论/提交/分支名，识别“实现但未用自动关闭关键词”的关联；
   4. 检查默认分支及相关分支提交历史是否已有实现或后续合并；
   5. 以上均无关联且数据访问无失败，才标记“无相关 PR/commit”。访问不完整/超时/失败时标记“关联状态待确认”，不列为干净候选。
   已关闭但未合并的相关 PR：单独报告其状态、关闭原因、是否保留实现分支、是否需等维护者意见再 follow-up。GitHub `Development` 区域与搜索结果可能不一致（权限/缓存/动态加载）；截图、页面关联、可打开的 PR 链接都是证据，不被“当前 API 返回为空”覆盖；冲突时保留两种结果、标注检查时间，取保守结论。
5. 回到本地源码核实每个候选 issue：定位相关文件、函数、测试、配置，说明问题为何真实存在；无法复现或证据不足标“待验证”，不当确定缺陷。
6. **强制上下游真实性核验**（不只凭单个函数/单段代码下结论）。对每个候选 bug、源码改进点和重要 feature：
   - 从入口（用户输入/API/事件/任务）向下追踪参数、状态、数据如何经过调用者/被调用者/队列/库/缓存/序列化/外部服务；再向上追踪谁消费、展示、触发后续。
   - 记录问题成立的前置条件、预期不变量与实际行为；检查上下游是否已做校验、归一化、重试、去重、限流、兜底或错误处理。
   - 搜全部直接调用者、同类实现、相关测试、配置默认值、部署路径，确认问题不在不可达代码、测试桩或废弃流程中。
   - 用最小复现、现有测试、日志/接口行为或静态链路证明影响；只能推测时标“推测/待验证”。有已有防御或相反证据时给出结论：真实存在 / 仅特定配置存在 / 已被上下游抵消 / 不成立；上下游信息不全时说明缺失环节与原因。
   - 若后续状态会重触发 effect/任务/请求/事件，检查是否导致重复执行、竞态或资源泄漏；有防抖/清理/幂等保护则纳入结论。
7. 查 roadmap、计划、RFC、讨论区、维护者公开规划，列出社区可实现且未完成的事项，区分“官方明确计划”与“基于源码推断的建议”；对 roadmap 事项同样检查代码、已有 PR、上下游依赖，避免推荐已实现或无法独立交付的。模块模式在模块清单阶段只记录帮助选范围的高层规划；深入核对等选定模块、形成候选后，只做该候选相关定向检查。
8. 深读与模式/范围相关的源码，找真实 bug、冗余/可精简接口、有明确价值的 feature。选项 1 的源码核验范围由全部 open Issue/PR 关联代码决定；选项 2 由选定模块决定（先源码后定向核对 GitHub）。参考优秀开源项目与高可信资料时给出来源链接并说明适配理由。任何源码发现先完成上下游核验再入候选；模块模式入候选后做 Issue/PR/commit 去重。
9. 为每个发现记录证据：issue/PR/commit/roadmap 链接、源码文件与行号、上下游调用链、前置条件、复现或推理依据、影响范围、置信度。不凭标题、单函数或搜索摘要下结论。
10. 按下方结构输出中文 Markdown 报告；没有可靠发现的类别写“未发现符合条件的事项”，不为凑数量猜测。报告加“调研进度与截止时间”小节，注明对应账本与轮次、截至时间、覆盖/未覆盖范围；账本与报告都保留，不得用报告替代账本。

## 判断原则

- “真实存在”必须同时有问题点和可达执行链：至少说明入口、关键中间处理、下游消费者、预期与实际差异。只有可疑代码、未证明影响真实流程的，最多列“待验证”，不推荐直接提交 PR。
- 不能因局部函数有风险就跳过上下游检查；确认调用方是否传入该值、下游是否已过滤/修正、错误是否被重试或吞掉、对应分支是否真会在生产配置执行。
- 不把代码风格偏好包装成 bug；每个 bug 至少有代码证据、可复现路径或明确的不变量冲突。
- 优先推荐小范围、可验证、符合项目当前架构的贡献；不引入全新框架或大型重构。
- 每个 fix 候选的人话版必须脱离项目背景独立读懂；术语只在首次带解释后使用；不得在无人话版的表格行里以一句“修复建议”了事。
- 研究资料只用于支持判断，不大段复制；链接直指原始 issue、文档、源码、PR、commit、项目或论文页。
