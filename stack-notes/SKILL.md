# 技术栈学习笔记

## 目标

把语言、框架、工具或技术栈整理成一份可以快速上手、又能建立整体认知的学习笔记。

默认读者已经有一门编程语言或后端开发经验，但不了解当前目标技术。例如：Java 后端开发者学习前端、Python 开发者学习 Go、传统服务端开发者学习 React。

笔记完成后，读者应当能够：

1. 搭建最小开发环境并运行代码；
2. 使用最常见的能力完成一个小型实际功能；
3. 解释主要代码为什么这样写；
4. 理解代码从输入到运行结果的主要链路；
5. 分清语言、运行时、框架、库、工具和平台的职责；
6. 知道下一步应该实践什么、深入什么。

不要以覆盖所有知识点为目标。这里的完成标准是“足以开始正确开发并继续深入”，不是“完整复述官方文档”。

## 支持的任务

本 Skill 支持四种任务：

- 从零创建一份技术学习笔记；
- 重构已有 Markdown，使其形成清晰教程；
- 合并多份笔记、资料和用户想法；
- 根据当前官方资料更新旧笔记，删除或标明过时内容。

用户可能只提供一个主题，也可能提供没有固定顺序的文件、链接、代码片段、问题和个人理解。不要沿用输入资料的随机顺序。先建立逻辑主线，再吸收其中有用的内容。

## 开始前的处理方式

### 存在现成 Markdown

先完整阅读目标文件和用户指定的参考资料，再给出重构方案。方案至少说明：

- 当前笔记的主要问题；
- 建议采用的逻辑主线；
- 章节如何保留、移动、合并、补充或删除；
- 预计补充哪些外部资料；
- 哪些内容会降级为“进一步了解”或删除。

给出方案后等待用户确认，再修改文件。

如果用户明确要求直接修改、不需要确认，则可以跳过等待，但仍要先在内部完成结构判断。

### 不存在现成 Markdown

根据主题直接建立合理骨架并开始编写。只有缺少的信息会显著改变笔记方向时才询问用户；其他情况根据默认读者和本 Skill 的原则继续推进。

## 工作流程

### 第一步：确定学习边界

确认以下信息，优先从对话和已有资料中推断，不要重复询问用户已经提供的内容：

- 学习对象及其版本；
- 它属于语言、框架、工具还是完整技术栈；
- 读者已有的相关基础；
- 目标是快速体验、项目开发还是知识迁移；
- 是否存在目标文件、参考资料和必须保留的内容。

如果用户没有指定版本，区分稳定原理与版本相关实现。涉及当前版本、工具链现状或已经变化的 API 时，查询当前官方资料。

### 第二步：建立逻辑主线

目录必须根据技术本身动态生成，不要强制套用固定模板。但整体应回答以下问题：

1. 它解决什么问题，适合什么场景？
2. 它处于整个系统的哪一层，依赖什么，又被什么使用？
3. 如何安装、运行第一个最小示例？
4. 日常开发最常用的概念和操作是什么？
5. 一段典型代码从编写到产生结果经历什么过程？
6. 它与相关工具、生态和部署环境怎样配合？
7. 初学者最容易混淆什么？
8. 完成入门后应该实践或深入什么？

根据学习对象调整重心：

#### 编程语言

通常关注：运行方式、基本程序、值与类型、控制流、函数、数据结构、模块、错误处理、异步或并发、包管理、构建和运行时。

#### 框架或库

通常关注：它解决的问题、项目创建、核心抽象、组件或模块组织、状态与数据流、生命周期、输入输出、一次更新或请求链路、常见生态和构建部署。

#### 开发工具

通常关注：输入和输出、安装、最常用命令、配置文件、一次完整工作流、它与上下游工具的关系、常见问题和产物。

#### 完整技术栈

通常从底层平台向上组织：语言和运行时、标准库或 Web 平台、框架、数据与通信、开发工具、构建产物、部署和运维。明确每一层负责什么，不要只罗列名称。

这些只是选材参考，不是固定目录。章节结构应服从目标技术的真实使用路径。

### 第三步：整理输入资料

对用户资料执行以下处理：

1. 提取有效事实、示例、疑问、经验和用户特别关心的主题；
2. 识别重复、过时、错误、互相矛盾和缺少上下文的内容；
3. 将内容放入新的逻辑骨架，而不是保留原顺序；
4. 保留有助于理解和实践的内容；
5. 删除不影响入门的边缘细节和重复解释；
6. 用户原有理解不准确时直接修正，并解释关键原因；
7. 不要因为参考资料篇幅很长，就按相同比例纳入新笔记。

### 第四步：补充和核对资料

需要外部资料时，优先使用：

1. 官方文档和语言标准；
2. 官方源码仓库中的架构或贡献文档；
3. 原始技术提案、发布说明和维护者资料；
4. 其他高质量资料。

搜索的目的包括：

- 确认当前推荐用法和版本；
- 核对架构、核心包和工具职责；
- 找出用户资料中的过时说法；
- 补足理解主线所必需的内容。

不要为了显示调研量而加入与入门目标无关的信息。版本相关结论应注明版本或附上来源；稳定概念不必每句话都附引用。

### 第五步：编写和重构

重要主题优先采用以下顺序：

```text
它解决什么问题
→ 实际如何使用
→ 最小关键示例
→ 示例中的关键代码是什么意思
→ 足以支撑正确使用的核心原理
→ 它在整体链路中的位置
→ 常见误区或下一步
```

不要机械地为每个知识点生成全部小节。简单概念可以用一段话说明，核心概念才需要完整展开。

## 深度控制

对准备加入正文的内容依次判断：

1. 完成第一个真实项目是否需要？
2. 是否影响对整体架构或运行流程的理解？
3. 是否容易因为不理解而错误使用？
4. 是否是继续学习的必要基础？

至少满足一项才进入主线。

以下内容默认不进入快速入门主线：

- 很少使用的语法和 API；
- 源码级内部数据结构；
- 完整的优化算法和调度算法；
- 不影响实践的历史版本细节；
- 罕见边缘情况；
- 只为显示完整而罗列的工具和包；
- 无法帮助读者理解或使用的伪源码。

有价值但暂时不必要的内容，可以简短放入“进一步了解”，或告诉读者后续应该搜索什么。不要让深入内容中断入门主线。

## 术语与解释规范

第一次提出重要术语时，根据需要解释：

- 它是什么；
- 它解决什么问题；
- 它属于系统的哪一层；
- 它在代码、命令或运行流程中在哪里出现。

不是每个单词都需要定义。重点解释会影响整体理解、正确使用或后续阅读的术语。

不要用另一个尚未解释的术语代替解释。例如不能只写“Vite 通过模块图进行 HMR”，而不说明模块图记录模块依赖关系、HMR 用于开发阶段局部更新模块。

提出抽象结论时，补充能支撑结论的最短解释。例如不能只写“框架是状态驱动 UI”，需要说明什么是状态、状态如何登记更新，以及最终由谁操作目标平台。

解释到能正确理解和使用为止。除非内部实现会直接影响使用，否则不要继续展开源码结构。

## 示例规范

示例应当：

- 使用当前常见、真实可用的写法；
- 尽量短，但完整表达当前知识点；
- 一个示例主要解释一个问题；
- 给关键代码添加注释或紧邻解释；
- 说明输入、关键过程和可观察结果；
- 避免加入与当前主题无关的工程代码；
- 需要多个文件时标明文件名和文件之间的关系；
- 简化实现时明确说明省略了什么，不能把概念代码说成完整源码。

优先给出读者可以修改和运行的例子。只有代码不能清楚表达执行顺序或层级关系时，才增加简短流程图或表格。

## 语言规范

- 使用直接、准确、自然的中文；
- 说清本质，但不使用比喻解释技术机制；
- 不堆砌术语，不用工具名称代替解释；
- 避免假定读者已经理解的“显然”“很简单”“只是”；
- 第一次出现的重要缩写应给出全称或中文含义；
- 同一概念使用稳定名称；
- 明确区分语言、运行时、宿主环境、框架、库、开发工具和平台；
- 优先使用短段落和有意义的小节，不把每句话都拆成列表；
- 不为了形式整齐强行增加重复总结。

## 修改已有文件时

- 保留用户有价值的内容和个人问题；
- 重排、改写和合并内容，而不是简单追加新章节；
- 发现重复时保留解释位置最合理的一份；
- 发现错误或过时内容时直接修正；
- 不覆盖无关文件，不修改用户没有纳入范围的内容；
- 如果文件已有主要框架，先判断它是否仍然适用，不要为了重构而完全推翻；
- 修改完成后检查标题层级、代码块、链接、术语顺序和上下文衔接。

## 输出要求

### 重构方案

已有 Markdown 时，方案采用以下结构，但可按任务删减：

```markdown
## 当前问题

## 建议主线

## 章节调整

| 现有内容 | 处理方式 | 原因 |
| --- | --- | --- |

## 需要补充或核对的内容

## 预计删除或降级的内容
```

### 最终笔记

最终笔记的目录动态生成，但正文通常应包含：

- 学习对象的定位；
- 最小可运行实践；
- 核心概念和常用操作；
- 一条完整运行或开发链路；
- 与相关生态的职责边界；
- 入门实践建议和下一步路线。

如果某一项不适合当前技术，可以省略。

### 完成说明

完成修改后简要说明：

- 重构或新增了哪些主线；
- 删除、合并或降级了哪些内容；
- 核对了哪些版本相关信息；
- 文件位置；
- 尚未处理且需要用户决定的问题。

## 完成前检查

逐项检查：

- 读者能否根据笔记运行第一个示例？
- 是否先给实际用法，再解释必要原理？
- 是否有重要术语在解释前被反复使用？
- 是否有抽象结论没有说明依据？
- 是否只有 API 罗列，没有整体链路？
- 是否讲了大量内部细节，却遗漏日常开发能力？
- 是否把开发阶段、构建阶段和运行阶段混在一起？
- 是否把语言、运行时、框架和工具混在一起？
- 是否存在重复、过时或互相矛盾的内容？
- 是否清楚说明了下一步实践或深入方向？
- Markdown 标题、代码块、表格和链接是否完整？

如果某段内容不能帮助读者上手、理解整体或避免重要误用，删除或缩短它。
